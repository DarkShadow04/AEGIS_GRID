# Audit & Test Findings — ShadowNexus v4 Rebuild

## Critical
1. **Exposed live API keys in public repos.**
   - `AbuseLPDB/AbuseIPDB.py` — hardcoded AbuseIPDB key committed to git history and current source.
   - `Dark_Console/dark_console.py` — hardcoded VirusTotal key committed to git history and current source.
   - **Action needed from you:** revoke/rotate both keys now. Anyone browsing the repo (or GitHub's own code-search) can read them.
   - Also worth doing: `git log -p` on both repos to confirm the keys aren't recoverable from old commits even after you edit the file, and scrub history (`git filter-repo` or BFG) if they are, then rotate anyway since scrubbing doesn't undo an exposure that already happened.
   - **How the rebuild prevents a repeat:** keys are entered once through the dashboard's Settings tab and saved to `backend/config/secrets.json` — never in source, never in git (that whole directory is gitignored), file permissions locked to owner-read/write only. The API only ever returns a masked preview (`fake****cdef`) plus a configured/not-configured flag, never the real value. A "Test" button per key makes one live call to that service to confirm it works, and the test result never echoes the key even on failure — verified directly: saved a test key, confirmed `chmod 600` on the file, confirmed the raw key never appears in any API response including a failed connectivity test.

## Bugs found and fixed during live testing
2. **Header-checker false negatives.** The original `headers_checker.py` copied `resp.headers` into a plain Python dict before comparing header names. `requests`' header object is case-insensitive; a plain dict isn't. Servers that return headers in lowercase (common over HTTP/2) were reported as missing *every* security header, even when present. Confirmed by testing live against `github.com` — it initially reported HSTS/CSP/etc. all "missing," which is wrong; GitHub sets all of them. Fixed by comparing against `resp.headers` directly (case-insensitive) instead of a flattened dict. Re-verified: correctly reports only `Permissions-Policy` missing on GitHub, and zero missing headers on `pypi.org`.

## Verified working (live tests, not just code review)
3. Nmap module: installed `nmap`, ran a real scan against `127.0.0.1` with the `quick` profile, confirmed valid XML parsing end-to-end.
4. IP reputation module: confirmed graceful, clear errors when `ABUSEIPDB_API_KEY` / `VIRUSTOTAL_API_KEY` are unset, rather than crashing.
5. System telemetry (`core/system_info.py`): confirmed real CPU/memory/uptime/network values via `psutil`, no placeholder data.
6. Health check (`core/health.py`): confirmed it correctly detects installed/missing dependencies (`nmap`, `cloudflared`) and configured/unconfigured API keys.
7. Full backend boot: all 13 API routes + WebSocket registered cleanly, ran under `uvicorn`, hit every endpoint over real HTTP with real responses.

## v6 findings — nmap custom commands, new modules, and a real UI bug

9. **Custom nmap commands needed real abuse-vector protection, not just parsing.** Since custom flags are now driven by a web API instead of a local terminal, I built an allowlist validator (`nmap_scanner.validate_custom_args`) and tested it against both valid commands and known abuse patterns: file-write/read flags (`-oN`, `-iL`), source spoofing (`-S`), decoy scanning (`-D`), idle-scanning a third party (`-sI`), path traversal into `--script` (`../../etc/passwd`), and a shell-injection-style token (`-p; rm -rf /`). All 11 abuse attempts were correctly rejected; all 9 legitimate commands passed. Verified the execution path too — a blocked command never reaches `subprocess.run`.

10. **Real UI bug found via actual browser automation, not just visual review:** the Nmap Command Library dropdown looked correct in every screenshot, but real mouse clicks on its items silently failed to fill the input — only discovered by testing with Playwright's synthetic mouse clicks (which simulate real cursor movement) rather than trusting a static code read. Root cause: the parent card's hover-triggered 3D tilt (`transform: perspective(...) rotateX(3deg) ...`) physically shifts everything absolutely-positioned inside it, including the dropdown, while the mouse is moving toward an item — so the item visually moves out from under the cursor mid-click. Fixed by locking the card flat (`transform: none`) via `:has(.cmdlib-panel.open)` whenever its dropdown is open. Re-verified with the same synthetic-click test: correctly fills `--script vuln` and `-A -T4` on selection now.

11. **SSL checker correctly detected this sandbox's own TLS interception** — when tested against `github.com`, the returned certificate issuer was Anthropic's own egress gateway, not GitHub's real cert. That's an artifact of testing inside a network-proxied sandbox, not a bug — but worth knowing so you don't mistake a proxy's cert for the origin's once you deploy this somewhere with normal network access.

12. **Full interaction test suite**, run headlessly (Playwright, Chromium): tab switching, chat panel open/close, command library open + real click-select, headers info modal open/close (including confirming it correctly blocks clicks to content behind it while open), quota tab populated from a live backend, zero JavaScript console errors across the whole sequence. Chart.js and Three.js couldn't be loaded from cdnjs.cloudflare.com in this sandbox (network is restricted to package registries here) — stubbed both for testing purposes; this is a sandbox limitation, not something that will affect your deployment, which has normal internet access.

## Known limitations (by design, not bugs)
8. Nmap scans against arbitrary remote hosts, and the AI analysis layer, weren't exercised against live external infrastructure in this environment — this sandbox's network is restricted to package registries. You should run the same smoke tests (`/api/scan/nmap` against a host you're authorized to test, `/api/assess/full` with `ANTHROPIC_API_KEY` set) once deployed on a machine with normal network access.
9. `mac_address_changer` logic wasn't wired into the web dashboard — changing a host's MAC address remotely, via a web endpoint, is a meaningfully different risk profile than running it locally at a terminal (it's effectively remote code execution over the network interface). If you want it exposed via the API, it needs auth in front of it first — see Next Steps in the README.
10. `InfoGate` wasn't ported. It's a Python 2 menu of `apt install` / `git clone` calls for third-party tools, several of which (`saycheese`, `locator`) are surveillance-adjacent rather than defensive. Nothing there was reusable logic, and I didn't rebuild the installer-wrapper pattern into the new framework.

## v7 findings — from live user testing on Kali

13. **Card hover-tilt blur, confirmed and fixed.** Hovering any card visibly blurred its text. Root cause: `perspective()` + `rotateX()` on `:hover` forces the browser to composite that element on a non-integer pixel grid — a well-known CSS rendering issue, distinct from an actual blur filter (there wasn't one). Fixed by dropping the 3D tilt from hover entirely, keeping a flat `translateY` lift + glow instead. Verified via computed-style inspection: the hover transform matrix now has zero rotation component.

14. **Tunnel URL showing literal "trycloudflare.com..." instead of a real link.** The original parser scanned cloudflared's stdout for the first line containing the substring `trycloudflare.com` — but cloudflared's own startup banner contains an unrelated docs-link mention of that domain before the real assigned subdomain ever appears, so the parser very likely grabbed the wrong line. Rewrote to match a strict URL regex on a background-threaded reader instead. Verified against a simulated realistic cloudflared output containing exactly that decoy line plus the real URL — now correctly extracts only `https://<real-subdomain>.trycloudflare.com`.

15. **Local server never showed a usable link.** `server_manager.status()` didn't return a URL at all — the dashboard could only show raw status text. Added a `local_url` field and wired it to a real clickable link.

16. **Chat errors were technically accurate but useless for diagnosis.** Every OpenAI/Gemini failure showed the same generic `429 Too Many Requests`, whether the real cause was rate-limiting, an unfunded/no-billing account, or something else — because `requests`' default exception message doesn't include the response body, which is where providers actually explain what happened. Fixed both clients to parse and surface the real error detail. Verified against mocked responses matching OpenAI's real `insufficient_quota` vs `rate_limit_exceeded` error shapes — now distinguishable.

17. **New: Reports tab with persistent history + TXT/PDF export.** Every scan across all 8 scan endpoints now saves to `core/history.py`, browsable in a new Reports tab, each exportable as a formatted TXT or PDF (headings, target, timestamp, command used, findings, footer). PDF export was tested with the actual jsPDF library pulled via npm (this sandbox can't reach cdnjs directly, same limitation as before) — confirmed it produces a valid, correctly structured PDF, not just that a download triggers.

18. **On the exposed API keys:** six live keys (Anthropic, OpenAI, Gemini, VirusTotal, AbuseIPDB, Hybrid Analysis) were pasted directly into the chat conversation. This is flagged as a real exposure — chat history is not equivalent to the secrets_store's local-file-only design this whole project has been built around, and treating it as a safe transfer channel defeats that purpose. None of the six were used in any test above; all reproduced errors were generated with mocked responses instead. All six should be rotated.

## v9 findings — rename, remote access, and bugs from your live testing round 3

19. **Critical: health check read the wrong source of truth.** `core/health.py` checked `os.environ.get(...)` directly, but every key configured through the Settings tab is saved via `secrets_store` to `config/secrets.json` — never as an actual environment variable. This meant the dashboard permanently showed every key as "not set," even immediately after saving and successfully testing it. Fixed by reading through `secrets_store.get_key()`, the same path every scan module already uses. Verified: save a key, health check reflects it on the next call.

20. **Remote/tunnel access was fundamentally broken, not just misconfigured.** The frontend hardcoded `API = "http://localhost:8000"`. When only the separate static-file workspace server was tunneled, the dashboard HTML loaded fine remotely, but every `fetch()` call still pointed at `localhost:8000` — meaning the *remote viewer's own machine*, not yours. Nothing could ever have worked this way. Fixed two ways together: (1) the backend now mounts the frontend directory as static files and serves it directly, so dashboard + API share one origin; (2) the frontend auto-detects `window.location.origin` instead of hardcoding localhost, falling back to localhost only when opened as a local `file://` page.

21. **Hybrid Analysis 400 error — root cause confirmed and fixed.** The original build called `/api/v2/quick-scan/url` without required parameters. Verified via search that full sandbox submission actually requires `POST /api/v2/submit/url-for-analysis` with an `environment_id`, then polling `/report/{job_id}/state` until `SUCCESS`, then `/report/{job_id}/summary`. Your own screenshots confirmed environment ID 160 = Windows 10 64-bit, used as the default.

22. **Nmap command library — declined additions, with reasoning.** Idle scan (`-sI`), decoy scanning (`-D`) with MAC spoofing, source-port manipulation, packet fragmentation, FTP bounce (`-b`), and `--script-args=unsafe=1` were requested but not added. These aren't "more aggressive scanning" — they specifically evade attribution or route traffic through/implicate uninvolved third-party hosts, which is a different risk category from scanning your own infrastructure hard. Added the legitimate parts of the same request (full port range, `-sV -O`, `--script vuln`) instead.

23. **Nmap timeout removed, replaced with a real background job system.** The flat 300s cutoff was killing legitimate full-port and vuln-script scans. Rebuilt as `core/job_manager.py` — a background thread per scan, live progress parsed from nmap's own `--stats-every` output, a Cancel endpoint. Verified end-to-end with a real nmap execution: correct status transitions (running → done) and correct final parsed result.

24. **Real UI bug found via actual browser automation (not caught by code review):** switching Command Library categories destroyed the very tab element the user had just clicked (the whole panel's `innerHTML` was rebuilt on every switch), which caused the outside-click-to-close listener to see a detached element and immediately close the entire panel. First attempted fix (using `event.composedPath()`) did not resolve it — actual root-caused by testing with real synthetic clicks, category switching, and DOM inspection together. Correct fix: stop rebuilding the tab bar itself on every category switch — only the item list underneath it changes now. Verified: panel stays open through category switches, item clicks correctly fill the input, and clicking genuinely outside the panel still closes it.

25. **Command Library visual glitch with the Hybrid Analysis card, root-caused.** An earlier attempt to fix this via `position:fixed` with manually computed coordinates introduced a *new*, worse bug (clicks landing on the wrong element entirely) — reverted. Correct fix: keep the dropdown `position:absolute` (simple, well-understood) and elevate the whole parent `.card`'s stacking context via `:has(.cmdlib-panel.open)` while open, so it wins against sibling cards regardless of DOM order — z-index on the dropdown alone only ranked it against its own card's children, not sibling cards later in the DOM.

26. **Settings input-overflow bug, root cause found.** A long API key (150+ chars) produced an equally long unbroken run of asterisks in the masked preview, and CSS grid items don't shrink below their content's intrinsic width by default (`min-width: auto`) — so the whole card, and the grid track containing it, stretched to fit. Fixed at all three layers: capped the mask preview length server-side, added `min-width: 0` to `.card` (the actual grid-overflow root cause), and `overflow-wrap` as defense in depth.

27. **AnyAPI added after verifying the real endpoint first** (`api.anyapi.ai/v1/chat/completions`, OpenAI-compatible) — learned from finding #21 above and checked before building instead of guessing.

## v10 findings — Hybrid Analysis removed, remote access, nmap expansion, headers

28. **Hybrid Analysis removed** at the user's request — it didn't fit the tool's actual needs. Every trace removed and verified (grep for any remaining reference returns nothing).

29. **The `-p80,443` bug, confirmed and fixed.** Nmap accepts port specs both attached to `-p` (`-p80,443`) and space-separated (`-p 80,443`) — the validator only handled the second form, silently rejecting completely valid, common syntax. Fixed with a dedicated regex for the attached form, extended to probe-type flags too (`-PS80,443` etc, which have the same attached-value convention).

30. **The nmap allowlist was expanded substantially** — roughly 5x more flags — covering ACK/Window/Maimon/SCTP scan types, all ping-probe variants, DNS/exclude/timing/performance tuning, version/OS-detection tuning, and `--script-args` generally (only the literal `unsafe=1`/`true` toggle stays blocked, since that specifically lets NSE scripts run checks that can crash the target service). Two categories remain excluded on purpose, not from general caution: arbitrary file read/write (`-oN`/`-oX`/`-iL`/etc — the tool already returns full results as JSON, nothing is lost), and attribution-evasion flags that specifically hide who's scanning or route traffic through/implicate an uninvolved third party (decoy, idle/zombie scan, MAC/source-port spoofing, fragmentation, FTP bounce). Verified: all new legitimate flags pass, the exact bug case passes, and all 15 previously-tested abuse patterns are still correctly blocked (regression-checked, not just re-asserted).

31. **Headers checker expanded from 6 to 29 headers**, covering the full list provided — but not as a blind copy. Corrected classification on several: X-XSS-Protection, Feature-Policy, Expect-CT, and the legacy X-Content-Security-Policy are deprecated by browsers/superseded by CSP or Permissions-Policy, and are now marked informational rather than "you should add this," which the pasted source's "Very Important"/"Necessary" labels would have gotten wrong. Public-Key-Pins is the sharpest case — it's actively dangerous today (removed from browsers, historically caused permanent site lockouts), so it's flagged as a finding only if *present*, never if absent. CORS, caching, and language headers are marked informational since their absence is completely normal outside specific contexts (APIs, sensitive-data caching). Verified live against github.com: correctly identified real gaps (missing COOP/COEP/Permissions-Policy) while correctly not penalizing it for lacking deprecated headers.

32. **Remote access got a real, dedicated feature** instead of relying on the general workspace tunnel (which exposes an unrelated static site, not the dashboard). New self-tunnel functions in `server_manager.py` with independent state, wired to a Start/Stop button in Settings.

33. **Chat expand bug, root-caused.** The toggle icon and the chat panel shared the same z-index, and the expanded panel's `bottom: 5vh` sizing extended it down into the same corner the icon lives in — so the panel (later in DOM order) painted over the icon. Fixed two ways: raised the icon's z-index above the panel's, and re-anchored the expanded panel to stay clear of the icon's corner entirely. Verified via `elementFromPoint` at the icon's exact screen coordinates while the panel was expanded — the icon itself is what receives the click, not the panel.

## v11 findings — the real nmap issue, and why it wasn't a "blocker"

34. **"Nmap not working" — actual root cause identified, not assumed.** Before touching anything, ran a real scan against a known target (`127.0.0.1`, guaranteed reachable) and inspected the raw XML directly. Confirmed: when every port nmap scans shares the same state, nmap's XML doesn't list them individually at all — it collapses them into `<extraports state="closed" count="1000"/>` with zero `<port>` elements. This is standard, correct nmap behavior, not a malfunction. The parser (`_parse_nmap_xml`) only ever read individual `<port>` tags, so a scan that ran perfectly and found "0 open ports, 1000 closed, host confirmed up" produced output *indistinguishable* from a scan that failed outright. Neither the flag allowlist nor the timeout was involved — removing either would have changed nothing, since the scan was already completing successfully.

35. **Fix: the parser now surfaces what nmap actually found.** Host up/down status and reason, whether the scan timed out on that host, the closed/filtered port summary, and top-level scan stats (hosts up/down, elapsed time) are all included now. A target with no open ports shows exactly that — clearly — instead of an empty array that looks broken. Verified against two real scans: an all-closed target (shows the full closed-port count and up status) and a target with a genuinely open port (shows the specific port correctly, confirming the fix didn't break the normal case).

36. Clear buttons added per-card across Security Sessions, plus one for the shared Session Output area — verified each resets only its own inputs/status, confirmed session output clearing doesn't touch the severity chart's underlying data source (history is untouched, only the current view).

37. 3D backdrop redone as a red-green duality pair (counter-rotating icosahedrons, mixed particle field) instead of a single-color shape — matches the tool's existing offense/defense red-green framing throughout the rest of the UI (severity colors, danger buttons) rather than introducing an unrelated third accent.

## v13 findings — Shodan integration

38. **Shodan's REST API contract verified before writing any code**, deliberately repeating the process that avoided a repeat of finding #21 (the original Hybrid Analysis endpoint being guessed and 400ing). Confirmed against Shodan's own developer docs: base `https://api.shodan.io`, key passed as a `key` query parameter on every request (no auth header), `GET /shodan/host/{ip}` for passive lookups, `GET /shodan/host/search` for credit-costing search, `GET /api-info` for free account/credit info, `POST /shodan/scan` (form-encoded `ips`) for on-demand active scanning, `GET /dns/resolve` for free hostname resolution.
39. **Credit accounting is approximate by design, and said so explicitly.** Shodan's real credit cost per call can exceed 1 (e.g. paginated or heavily faceted searches), but the quota tracker only counts calls, not Shodan's own returned credit balance. Rather than present this as exact, `account_info()` (backed by the free `/api-info` endpoint) is exposed directly in the UI as a "Check Credits Remaining" button so the real number is always one click away, alongside the approximate tracker.
40. **Host lookup and DNS resolve were deliberately left off the quota tracker** — both are genuinely free per Shodan's own billing, and gating them would have meant either a fake limit or extra state with no real quota behind it. Confirmed via the docs, not assumed from the "everything to same tier" pattern the other integrations follow.

## v14 findings — chat response modes + the actual Ollama timeout bug

41. **"Ollama not working" — root cause identified from your own screenshot, not assumed.** The error text (`Read timed out. (read timeout=120)`) combined with the fact that the same model was responding fine in a separate terminal chat pointed at generation time, not a broken connection: `ollama_client.py`'s `requests.post(...)` had a flat 120s timeout on a synchronous, non-streaming call. With this tool's attached context (log tail, health check, quota summary) added on top of the user's actual question, a CPU-only local model can legitimately take longer than that to finish — the request was being killed mid-generation. Fixed by raising the timeout to 600s; this is a ceiling increase, not a root fix for slow hardware, and is flagged as such.
42. **Chose a client-side elapsed-timer indicator over true token streaming, and said why.** Real per-token streaming from Ollama (its API supports `stream: true` NDJSON) would give more accurate live feedback, but wiring that through would mean a new WebSocket endpoint and a materially different request lifecycle — a bigger, riskier change to make without being able to test it against a live Ollama instance from this sandbox. The staged `⟳ <stage>... Ns` indicator (backed by real elapsed time, not fake progress percentages) solves the actual complaint — "it looks frozen with no feedback" — without that risk, and the gap to real streaming is called out explicitly in CHECKLIST.md rather than left implied as done.
43. **PoC response mode scoped to structure, not exploit code.** Instructed to produce a consistent per-finding breakdown (issue, component, preconditions, exploitation mechanism, impact, remediation) — the same shape a pentest report already uses — but explicitly told not to produce working exploit code or weaponized step-by-step commands, matching the authorized-testing framing already applied to nmap and the new Shodan scan endpoint elsewhere in this tool.

## v15 findings — Access & Limits (editable timeouts, visitor log)

44. **A real concurrency bug, not a theoretical one — found by actually testing under load, not just reasoning about the code.** The access log's read-modify-write to its JSON file had no lock. A quick single-threaded test looked fine; only running 10 threads × 30 writes concurrently exposed the race (entries silently dropped when two writes landed at once). Fixed with a `threading.Lock` around the load+append+save, and applied the same fix to `runtime_config.py` pre-emptively since it has the identical pattern, even though it's changed far less often.
45. **A design bug that unit tests alone wouldn't have caught.** Checking the `access_log_enabled` flag *inside* `record()` meant the very request that disables logging flips the flag before its own middleware-side log write runs — so turning logging off silently erased the evidence that it had just been turned off. This only showed up when testing the actual disable/enable sequence end-to-end against a live server and counting events, not from reading the function in isolation. Fixed by moving the on/off decision to before the request is handled, then adding one deliberately unconditional log entry specifically for this toggle (in both directions) so there's always a clear "logging turned ON/OFF here" line in the record — the property that mattered (nothing important silently disappears) was checked directly, not assumed from the fix looking plausible.
46. **Geolocation and IP-source caveats stated in the UI itself, not buried in a doc.** The Access Log card's own status line spells out that IPs come from X-Forwarded-For/X-Real-IP with a raw-socket fallback (so a tunnel that doesn't set those headers will show every visitor as the same address), and that location is an approximate free lookup, not authoritative. Someone using this feature to "keep an eye on" shared access needs that caveat at the point of reading the data, not just in README.
47. **Every visitor-controllable field gets HTML-escaped before it touches `innerHTML`.** Once this is tunneled and shared, the request path, forwarded IP, and geoip response are all attacker-influenceable to varying degrees — treated as untrusted input into the admin's own dashboard rather than assumed safe just because the data's going into a "log," and escaped accordingly with a small helper rather than trusted template strings.
